## CONTRADICTIONS

Two verified facts contradicted statements the four docs relied on. Both were
raised, both were decided by the operator on 2026-09-03, and **both decisions
are now applied across the four docs.** The original findings are kept below in
full rather than rewritten, because the reasoning is the record.

### Decisions taken

**C-1 resolved: layered, not a single mechanism.** D4 and D7 now state plainly
that `timeoutMs` is an idle timer and not a wall clock, and is therefore not a
backstop on its own. Three independent layers replace it. Layer 1, primary: the
expiry sweeper calls `kill()`, unchanged. Layer 2, backstop A: a guest-side
self-destruct scheduled by the boot script stops the app process at a fixed
wall-clock deadline, and this is the only layer indifferent to visitor activity,
which is what T1 and T2 need since a miner is active by definition. Layer 3,
backstop B: `timeoutMs` 180 s with `onTimeout: "kill"`, refreshed by a 45 s
server heartbeat tolerating two misses, so worst-case overrun after server death
is 3 minutes, `0.057 x (3/60) = $0.0029`. `onTimeout` is `"kill"` for every
visitor instance and never `"pause"`, because a paused zombie neither bills nor
counts against concurrency and would therefore be invisible and permanent;
`pause` stays reserved for the warm pool. The preview-traffic question is
numbered **Q17** and measured inside G3 as its own sub-measurement (fork, drive
HTTP through `previewUrl` continuously with no SDK calls, see whether it dies at
`timeoutMs`). The docs state explicitly that the design no longer depends on the
answer. Written into `02-architecture.md` section 8.2, `01-prd.md` F6 and
section 11, and `03-security-and-access.md` section 3. The security doc also
records that the v1.5 `pty` terminal defeats layers 2 and 3, so terminal sessions
run as a non-root user, or terminal instances get a 5-minute lifetime and no
network.

**C-2 resolved: counting fetch.** The injected `fetch` becomes the single choke
point where the guard, the per-call deadline and the ledger live, since it is the
only place that sees every real HTTP attempt. Retry caps per call class: **0**
during gates so G1 measures real latency, **1** for `create` (the idempotency key
makes one 503 retry worth having), **0** for anything that spends money without
an idempotency key. Every call carries an `AbortSignal` tied to the launch
deadline, so a retry can never outlive the timer the visitor is watching. Two
unit tests against a fake `fetch`, zero credits: a 429 produces exactly one
attempt, and a 503 produces the documented retry count. The SDK version is pinned
in the lockfile and those two tests are the regression guard, given that
`http.js`'s header comment contradicts its own code. G1 samples record attempt
counts; a sample with `attempts > 1` is flagged, not dropped, and the report gives
p50 and p95 both with and without them. Written into `02-architecture.md`
sections 8.1, 13 and 14.

**Two further decisions taken at the same time, not contradictions but scope:**

- **G1 gets a written kill criterion.** Snapshots carry memory as well as disk
  (V22), so cold fork may land within noise of warm resume. If **cold p95 is
  within 500 ms of warm p50**, the warm pool is deleted from v1: D2, the warm pool
  manager, the replenish path and its reconciler all come out, and the cold number
  becomes the headline. The gate report states the verdict explicitly rather than
  leaving it to be inferred.
- **G6 does not only look for a platform feature.** It tests whether the boot
  script can install `nftables` deny-all-outbound-except-loopback inside the
  sandbox, and whether a non-root app user can remove them. Visitors have no shell
  in v1, so a guest-side firewall is a real control. The CPU cap is the fallback
  only if that test fails.
- **Q6 insurance is built now.** The Solari adapter takes a key per call, passed
  in, never read from the environment at the call site, making bring-your-own-key
  a config flip rather than a v2 rewrite. `01-prd.md` section 10.1 carries the
  BYO-KEY FALLBACK: if no written permission has arrived by day 5, the site ships
  live with catalog, health wall, canary log and recording all real, and Launch
  asks the visitor for their own key, held in session, never written to Postgres
  or logs.

### C-1. `timeoutMs` is an idle timer, so the Solari-side backstop in D4 and D7 does not hold for an active visitor

**What the docs say.** `02-architecture.md` section 8: "sandboxes are created
with `lifecycle: {onTimeout: "kill"}` and a `timeoutMs` slightly above the
maximum instance lifetime, so Solari's own timeout is the last line of defence
if the Blink server dies." `03-security-and-access.md` section 3 lists
"10-minute lifetime, one extension, hard kill, plus `lifecycle: {onTimeout:
"kill"}` set on the sandbox so Solari kills it even if the Blink server dies"
as the mitigation for T1 (mining), T2 (outbound proxying), T3 (malware hosting)
and T6.

**What the source says.** `https://docs.getsolari.com/sandboxes`, checked
2026-09-03: "Set `timeoutMs` to say how long it can sit **idle**; every action
and open connection resets the clock." Default is 30 minutes if unset. Also
confirmed: `onTimeout` defaults to `"pause"`, not `"kill"`, so setting `"kill"`
explicitly is correct and necessary.

**Why it contradicts.** `timeoutMs` is not a wall-clock lifetime cap. It is an
inactivity timer that every action and every open connection resets. Set
"slightly above the maximum instance lifetime" (roughly 21 to 25 minutes), it
fires only after 21 to 25 minutes of total inactivity. The scenario the control
was written for is the Blink server dying while a visitor is still using their
instance, and in exactly that scenario the visitor's own activity keeps
resetting the timer. The backstop is weakest precisely when it is needed. The
same reasoning weakens the T1 and T2 mitigations, since a miner or a proxy user
is by definition active.

**Unknown that makes this sharper.** It is not documented whether HTTP traffic
to a `previewUrl` counts as an "action" or an "open connection" for the idle
clock. If it does, no server-side scheme can guarantee the sandbox dies while a
visitor keeps loading pages. This is a new question and it needs a gate. I
propose numbering it **Q17** rather than adding it silently: "Does traffic to
`previewUrl`, and does an open control channel, reset the sandbox idle clock?"
It folds naturally into G3.

**Options, none taken.**

- (a) Accept, and rely on the Blink server's own expiry sweeper plus the 60
  second reconciler, documenting the residual risk that a dead server leaves
  active instances running until the reconciler returns.
- (b) Invert the control into a dead-man refresh: set a short `timeoutMs` (say
  90 seconds) and have the server call `setTimeout` on a heartbeat. Server death
  then fails closed. This only works if visitor traffic does not itself reset
  the clock, which is Q17.
- (c) Accept and state it plainly on the security page as a known limit.

**My recommendation: (b), conditional on Q17.** It is the standard dead-man
pattern and it makes server death fail closed instead of fail open. But it
changes what D4 claims about how lifetime is enforced, so it is your call, not
mine.

### C-2. The Solari SDK retries idempotent requests five times by default, and `SandboxClient` exposes no way to turn it off

**What the rule says.** Your instruction for the harness: "There is no retry loop
anywhere in this codebase, now or later." `02-architecture.md` section 8 states
the same for D7: "there is no retry loop anywhere in the codebase (G7)".

**What the source says.** From the published `@solarisdk/core@0.1.2`:

- `http.d.ts`: `maxRetries` is documented as "Max retry attempts for idempotent
  requests. **Default 5.**"
- `http.js` header: "idempotent requests (GET, DELETE, or any request carrying
  an Idempotency-Key) are retried on network errors, HTTP 5xx, 429, and bodies
  flagged `retryable`, with exponential backoff + jitter."
- `http.js` backoff: `150 * 2 ** attempt` capped at 8000 ms plus up to 250 ms
  jitter, so 150, 300, 600, 1200, 2400.
- `sandbox-client.js`: `create()` sends `idempotencyKey: newIdempotencyKey()` on
  every call, which marks it retry-eligible.
- `sandbox-client.js` constructor: `HttpTransport` is built with only
  `{apiKey, baseUrl, fetch?}`. **`maxRetries` is never forwarded.**
  `SandboxClientOptions` is `{apiKey, baseUrl, fetch?, callTimeoutMs?}`, so
  there is no public option that disables the retry.

**Why it contradicts.** A `create()` that meets a 503 `NoCapacity` or any body
flagged `retryable` is retried up to five times over roughly 8 seconds inside
the SDK, invisible to the budget guard and to the gate timer. The guard's cost
model and G7's "is the 429 immediate" measurement both assume one call is one
attempt. The invariant as written is false by default and cannot be made true
through the SDK's public options.

**What survives.** D7's specific claim about 429 is intact and now confirmed at
two levels. `http.js` excludes 429 from retry in the implementation, commenting
"NOT 429 that's our ConcurrencyLimitError (org at its session cap); retrying
won't help", and `docs.getsolari.com/errors` says "Retrying cannot help: a slot
only frees when _you_ pause or kill a session." Note that the `http.js` file
header comment claims 429 **is** retried and is contradicted by the code twenty
lines below it. The code is authoritative. Nobody should trust that comment.

**Options, none taken.**

- (a) Inject a counting `fetch` through the exposed `fetch` option in
  `src/solari/`, refuse any second attempt, and surface a retry attempt as a
  guard bug. Keeps the invariant literally true at the process boundary.
- (b) Relax the rule to "no retry loop that we write; the SDK transport retry is
  suppressed by fetch injection".
- (c) Accept SDK retries for 5xx only and state it in the doc.

**My recommendation: (a).** It is a few lines in the adapter, it keeps the stated
invariant true, and it makes G7 measure what it claims to measure. It also gives
the harness a natural place to count and report attempts.
