# G8: Uptime Kuma origin check through a real browser

**Question.** Does a real browser's WebSocket survive Uptime Kuma's Origin check behind previewUrl (Q20), given that Node cannot send an Origin header and therefore cannot test the branch that rejects one?

**Verdict.** Q20 RESOLVED POSITIVE. A real Chromium page loaded from the preview origin opened a WebSocket to Uptime Kuma and received an engine.io OPEN packet. The browser supplied the Origin header itself, so the branch that V68 could not reach, origin present and compared against Host, was exercised and passed. The preview domain presents Host and Origin consistently to the guest. Uptime Kuma is shippable as a catalog card without disabling its origin check.

**Observations.** 1 browser handshake through previewUrl, against a declared minimum of 1.

Run `g8-2026-09-04T06-37-14-252Z` on plan `starter`, 2026-09-04T06:37:37.099Z.

## What was asked

A real Chromium page was navigated to the instance's `previewUrl`, so the page origin IS the preview
host, and the WebSocket was opened from inside that page. The `Origin` header was therefore generated by
Chromium rather than by us, which is the only way to exercise the branch that matters.

## Why V68 was not enough

Uptime Kuma's `allowRequest` permits polling unconditionally, permits a WebSocket with **no** Origin
header explicitly, and otherwise requires `origin.host === req.headers.host`. Node's `WebSocket` sends no
Origin and offers no way to set one, so V68 took the allowed-with-no-origin branch. The check that would
reject a browser was the one that probe could not trigger.

| admitted | yes |
| reason | OPEN packet |
| fork to healthy | 1147 ms |
| bypass flag used | no, deliberately |

The workaround `UPTIME_KUMA_WS_ORIGIN_CHECK=bypass` was not used. It disables a cross-site websocket
hijacking defence, and turning off a security control to make a demo work is how a demo becomes the
reason for an incident.
